## 3. 問題別の詳細

### 001 OAuth 2.0 認可コードの横取り（c01）
- **判断の要点**：①表2のログから、c-71aが別IP・別User-Agentから1秒で交換されていることを読み取る。正規アプリによる交換要求（及びその失敗）が無いことから、レスポンスが横取りされたと推論する。②表1の「パスワード変更時にトークンを失効させない」設定から、初動はRT-1の個別失効となる。③stateも完全一致照合も効かない攻撃なので、PKCE S256の**必須化**が再発防止策になる。
- **難易度の根拠**：ログ・設定表・利用者申告の3資料を照合しないと、初動を決められない。誤答のnonce・有効期間短縮・IP遮断は、いずれも「対策らしく見える」もの。
- **検証**：ログの時刻差（1秒＜5秒）、正規アプリによるc-71a交換記録の不在、RT-1の使用がAT有効期間（10分）経過後であること、を自動検査。PKCEの効果はRFC 7636・RFC 8252の脅威モデル（不正アプリは認可レスポンスしか見られない）と整合する。
- **未確認事項**：なし。ただし、PKCEの`plain`方式もこの脅威モデルでは有効なため、あえて選択肢に入れていない（入れると一意性が崩れる）。

### 002 DMZ侵害後の到達可能性（c02）
- **判断の要点**：ルールを上から順に評価すると、No.10（NTP許可）はNo.6に隠れて（シャドウイングされて）一度も適用されない。ステートフルインスペクションは応答パケットだけを許可する（⑤）。同一セグメントの通信はFWを経由しないが、プロキシ側の接続元制限で拒否される（⑥）。キャッシュDNSの再帰問合せとNo.8を組み合わせればDNSトンネリングが成立する（④）。
- **難易度の根拠**：図・FWルール11行・サーバ設定・候補6件の照合が必要。FWルールだけを見ると②⑥を含めやすい。
- **検証**：FWルールを先頭一致で評価する模擬実装で①〜⑥を判定し、到達可能＝①④を確認した（②はNo.6で拒否されることも出力で確認）。

### 003 AWSのポリシー評価（c03）
- **判断の要点**：Conditionブロック内のAND評価と、否定形演算子は**キーが存在しないと真**になる仕様（④は拒否、③は拒否されない）。クロスアカウントでSSE-KMSを使う場合は、キーポリシーとIAMポリシーの双方での許可が必要（③）。既定の暗号化を変えても、既存のSSE-S3オブジェクトはKMS不要のまま（⑤）。SCPのDenyはどの操作にも該当しない。
- **難易度の根拠**：JSONポリシー5本・設定表・オブジェクト表・操作6件。サンプルの問2と同等以上の資料量である。
- **検証**：ポリシーの評価論理（明示的拒否の優先、SCPは組織内のプリンシパルだけに適用、同一アカウント／クロスアカウントの許可要件、KMSの許可要件）を実装した評価器で、図1〜図5のJSONを直接読み込んで判定した。結果は①SUCCESS、②暗黙の拒否、③KMSで拒否、④明示的拒否、⑤SUCCESS、⑥明示的拒否。
- **一次資料との照合**：否定形演算子とキーが存在しない場合の扱い、クロスアカウントのKMSでキーポリシーとIAMポリシーの双方が必要なことを、AWS公式ドキュメントで確認した（出典は本レポート末尾）。
- **未確認事項**：実際のAWSアカウントでの実行検証は行っていない（模擬評価器による検証）。

### 004 ADインシデントのタイムライン（c04）
- **判断の要点**：4769の暗号化タイプがRC4（0x17）かAES（0x12）か、表1のgMSAかどうか・パスワード強度、そしてその後の実ログオン（No.6）から、横展開に使われたのはsvc_backupと分かる。FS01にはadm_satoの「切断」されただけのRDPセッション（4779、ログオフ記録なし）が残っていた。そこでLSASSダンプ（comsvcs MiniDump）→NTLMでDCへログオン（PtH）という流れになる。4662のレプリケーション拡張権限GUIDはDCSyncを示すので、krbtgtを2回リセットする必要がある。
- **難易度の根拠**：ログ13行・注記4件・アカウント表・値の対応表を照合する必要がある。「切断はログオフではない」「PC-031から盗られたのではない」「DCSync→krbtgt」という、3段階の推論が必要。
- **検証**：時系列の順序、GUID、ログオン記録の有無を自動検査した。GUIDの意味とDCSyncの検知方法は、Elastic社の検知ルールの文書と照合済み。
- **未確認事項**：実環境でのイベントの再現は行っていない。4769の「サービス名」にgMSAを`svc_sql$`と表記している点は実ログに準じた表現だが、環境によって表示が異なる場合がある。

### 005 DMARCの判定（c05）
- **判断の要点**：SPF（aspf=r）とDKIM（adkim=s）で異なるアラインメントモードを適用する。CIDRの範囲計算として、203.0.113.32/28は.32〜.47、198.51.100.0/25は.0〜.127。p=reject化と同時にstrict化したことが、M3の不達原因になっている。
- **難易度の根拠**：DNSレコード7行とメール6通（6列）を突き合わせる必要がある。計算と規格知識の両方が求められる。
- **検証**：SPF（includeの再帰を含む）とDMARCのアラインメントを実装して判定し、pass＝M1・M2・M5を確認した。M3がadkim=rならpassすることも確認した（strict化の影響の裏付け）。
- **一次資料との照合**：relaxed＝組織ドメインの一致、strict＝完全一致。2026年5月にDMARCの新RFC（RFC 9989。RFC 7489を廃止）が発行されている。組織ドメインの決定方法が変わったため、事例の注記2で組織ドメインを明示し、どちらの規格でも結論が変わらないようにした。

### 006 SSRF（c06）
- **判断の要点**：`endswith("pcdn.example")`は「xpcdn.example」にも一致する（ラベル単位での比較になっていない）。URL中の`@`より前はユーザー情報として扱われる（P2）。requestsは既定でリダイレクトに追従し、リダイレクト先は検査されない。WAFは利用者のリクエストしか見ない。IMDSv2をrequiredにすれば、トークンなしのGETには401が返る。
- **難易度の根拠**：コード・環境設定・試行パターン4件を組み合わせて読む必要がある。「(B)を強化すればよい」「WAFを強化すればよい」という誤答がもっともらしい。
- **検証**：**図1の実装を実際に実行**して確認した。模擬IMDS（optional／required）と302を返す模擬サーバをローカルに立て、P1〜P4の挙動を観測した。結果は、P1＝WAFで遮断、P2・P3＝(A)で拒否（400）、P4＝認証情報を取得。対策bではP4を防げず、対策aでは401になって取得に失敗した。
- **作問上の修正**：検証の途中で、P3の初版（`img.pcdn.example.xpcdn.example`）が(A)を通過し、正答が二つになる欠陥を検出した。P3を`img.pcdn.example.evil-cdn.example`に差し替え、再検証で一意性を確認した。
- **注意点**：Pythonの`ipaddress`では、文書用アドレス（198.51.100.0/24など）が`is_private=True`になる。このため、診断員のサーバは具体的なIPを書かず「グローバルIPアドレス」と記述した。
- **未確認事項**：模擬環境ではTLSを省略している（P4をhttpで実行）。requestsがhttps→httpのリダイレクトにも追従することは仕様上確認済みだが、実際のEC2上での実行は行っていない。

### 007 ランサムウェアからの復旧時点（c07）
- **判断の要点**：スナップショットの7世代保持（11/11〜11/17が残る）と、NAS上のバックアップ2世代保持（11/1世代は11/15のフル完了まで残る）を組み合わせる。すると、11/11〜11/14のスナップショットに11/1世代の増分が含まれることが分かる。改ざんの開始（11/5 14:20）より前で最も新しい時点は、11/4 22:00になる。
- **難易度の根拠**：誤答の典型はイ（「NASは全滅、WORMの11/1フルしか使えない」）とキ（「最新のバックアップに戻す」）。日付・曜日・世代を手で追跡する必要がある。

## 8. データ構造（Webアプリ担当者向け）

### cases.json
- ルート：`setId`, `schemaVersion`（1.0のまま）, `language`, `exam`, `part`, `generatedAt`, `cases[]`
- 事例：`caseId`, `caseType`（`"single"`｜`"multi"`）, `problemNo`（multiだけに付与。9〜12）, `title`, `domains[]`, `body[]`
- `body` のブロック型：`paragraph`, `heading`, `table`, `code`（language：json / python / dns / javascript / yaml / nginx / text）, `list`, `diagram`, `box`（第1段階と同じ。新しい型は追加していない）

### questions.json
- 設問：`questionId`, `caseId`, `format`（全設問 `"single"`＝正答が一つの択一）, `order`, `stem`, `stemBlocks[]?`, `choiceFormat`, `choiceHeaders[]?`, `choices[{id, text, cells[]?}]`, `answer`, `explanation{summary, rationale[], distractors[]}`, `tags[]`
- **追加項目（後方互換）**：1問3答の設問だけに `problemNo`（大問番号）、`partNo`（大問内の設問番号1〜3）、`partCount`（3）を付与した。既存の001〜008にはこれらの項目がない。アプリ側では、未定義なら「`problemNo` = `order`、単独設問」とみなせばよい。
- 第1段階で予告した `format: "multi-part"` と空欄記法 `{{blank:…}}` は**採用しなかった**。独立採点の要件に合わせ、各設問を通常の択一（single）とし、大問との関係は `caseId` と `partNo` だけで表す。12設問は個別に抽選・採点でき、3問まとめて解答する前提の構造は持たない。

## 9. 未検証事項・制約
1. **実環境での実行はしていない**：実際のAWS・Active Directory・GitHub Actions・パッケージインデックスでは実行していない。代わりに、論理を実装した模擬評価器、実コードの実行（問6・問9）、実際のOpenSSLハンドシェイク（問11-2）で検証した。
2. **013**：GitHub Actionsの挙動は公式文書に基づく規則判定であり、実リポジトリでの再現はしていない。フォークからのpull_requestにシークレットが渡されないことは、GitHub文書を引用する二次資料で確認した（公式本文の該当箇所は、今回は直接取得していない）。GitHubの仕様は変わることがあるので、出題前に公式文書を再確認することを推奨する。
3. **016**：nginxではなく、同じOpenSSLの `s_server -serverpref` で交渉を再現した。nginxの `ssl_prefer_server_ciphers on` は、OpenSSLのサーバ優先オプションと同等である（作問者の知識による）。
4. **017**：表5の試行速度は事例上の仮定値であり、実機のベンチマークではない（計算自体は検証済み）。
5. **019**：ctimeを利用者が任意に設定できないこと（システム時刻の改ざんや、ファイルシステムを直接編集した場合を除く）は、一般的なLinuxの仕様として作問者の知識で判断した。事例の注記に前提として明記している。
6. **009〜011**：jsonwebtokenとExpressの挙動はスタブで再現した。実ライブラリでの結合試験は行っていない。
7. 難易度は作問者の判断であり、受験者データによる較正はしていない。表記はIPAサンプル（全角コンマ「，」、登録セキスペ等）に合わせた。
